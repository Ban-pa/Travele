# 智能旅行规划应用 · 整体设计（v0.2）

> 本文档写"现在是什么样、为什么这么定"。**代码是唯一的真相**，本文档与代码不一致时以代码为准。
> 还没做的部分明确标【未做】，不写成已完成。

## 0. 项目定位

- 形态：Web App（FastAPI 后端 + 纯静态前端，一个页面四个视图）
- 定位：实习 / 简历级完整项目，工程化程度与"取舍理由"是主要卖点，不追求商业规模
- 核心叙事：**LLM 负责创意与编排，系统负责正确性** —— 模型只决定"去哪几个点、怎么排、为什么"；
  坐标、规范名称、交通耗时与价格、时段这些事实由后端按目录和距离补齐；
  模型排不出来就老实报错，不拿机器凑的行程顶上
- 速度：排一次行程实测 **18~42 秒**（并行预取外部事实 + 规划关掉思考 + 后端自修少触发回喂）

## 1. 现有资产

**离线侧（`Travele/ingest/`）：用户的原始入库管道，保持不动。**
Streamlit 上传页 + 递归切分 + 本地 bge 向量化 + Chroma 持久化 + md5 去重 + 从正文提取城市。
定位：攻略文档是源代码，向量库是编译产物，在线侧只消费构建结果。

**在线侧：一条完整链路已经跑通。**
提交 → 装配（目录 + 召回）→ 模型排行程 → 后端补事实 → 7 类校验 → 前端交互 → 确认返回。
实测一次真实模型运行 40~60 秒，能排出一份 `validated=true` 的三日行程。

## 2. 总体架构

```
┌─ 前端 static/（纯 HTML/CSS/JS，无构建步骤）───────────────────┐
│ 一个页面四个视图：首页(#/home) / 目的地(#/discover) /           │
│                   路线(#/plan) / 手记(#/history)               │
│ 风格：旧地图旅行手账（Tailwind CDN + Google Fonts + Lucide）    │
│ 需求表单 → 进度条 → 可点的方案树（换地点/换交通）→ 确认结果     │
└──────────────────┬──────────────────────────────────────────┘
                   │ REST + SSE（202 任务 + 进度事件 + GET 结果）
┌─ 接入层 api/main.py ────────────────────────────────────────┐
│ 契约校验(422) / 提交预检(400) / 任务表(内存) / 统一错误体      │
│ 托管静态页 / 启动时预热嵌入模型                               │
└──────────────────┬──────────────────────────────────────────┘
┌─ 规划域 planning/ ──────────────────────────────────────────┐
│ 装配（目录候选点 + 攻略召回）→ 模型排行程（两档，各 3 次）      │
│   → 草稿转成品（后端补事实、剔除目录外的点）→ 校验（7 类规则）   │
│   → 结果存内存 → SSE: done；排不出来 → SSE: failed            │
└──────────────────┬──────────────────────────────────────────┘
┌─ 确认（用户改完节点之后）────────────────────────────────────┐
│ 决策表合并 → 解说 Agent：后端备事实（行程/地点/攻略/天气）→ 模型写介绍与建议 │
└──────────────────┬──────────────────────────────────────────┘
┌─ 数据与检索 ────────────────────────────────────────────────┐
│ Chroma（rag_cosine，离线构建）+ 本地 bge-small-zh-v1.5        │
│ data/destinations.json（21 城 36 点：坐标/开放时间/常规时长）  │
│ 任务与行程只放内存（进程重启即丢，现在没有数据库）             │
└────────────────────────────────────────────────────────────┘
```

## 3. 四个视图（一个前端）

| | 首页 | 目的地 | 路线 | 手记 |
|---|---|---|---|---|
| 场景 | 打开本子先看一眼 | 不知道去哪、想先看看 | 已经知道去哪 | 想翻以前确认过的 |
| 数据 | `spots.json`（封面照贴 6 张）+ `GET /api/plans`（最近 3 条） | `static/data/spots.json` 洗牌，零请求、零 LLM | 用户填表 + 后端规划 | `GET /api/plans` + `GET /api/plans/{id}` |
| 交互 | 两个入口按钮（翻开照片墙 / 直接排行程） | 一次看一个，不喜欢就换（一轮内不重复）→"就它了"或点照片墙任一张，把省市写进表单 | 填表 → 生成 → 进度 → 方案树 → 确认 → 解说 | 点一条看完整那一版（只读），可返回列表 |

四处汇合在同一个提交契约、同一条后端链路。视图切换靠地址栏 `#`，刷新不丢当前视图；
样式走 Tailwind CDN + 三个手写中文字体（Ma Shan Zheng / ZCOOL XiaoWei / Noto Serif SC）+ Lucide 图标，
纸张、胶带、宝丽来、印章、旧地图这些质感写在 `static/app.css` 里，不用外部图片。

## 4. 数据契约（camelCase；日期 `YYYY-MM-DD`；金额=元整数 + estimate 标记）

对外结构统一走 `WireModel` 基类：出去是 camelCase，进来 camelCase / snake_case 都认，
并且 **`extra="forbid"`** —— 字段名拼错立刻报错，不被静默忽略。

### 4.1 前端提交 `POST /api/trips`

```json
{
  "mode": "explicit",                    // "explicit" | "discover"
  "schedule": { "tripStart": "2025-08-01", "tripEnd": "2025-08-03" },
  "user": {
    "adults": 2, "children": 0,
    "departureCity": "杭州",
    "budgetTier": "mid"                  // 选填，前端不填就发 null
  },
  "destination": {
    "province": "云南",                  // 必填
    "city": "大理",                      // 必填
    "centerPlace": null,                 // 选填
    "mustVisit": []                      // 选填：必去地点（硬约束）
  },
  "isSelfDriving": false,                // 必填
  "prefs": { "themes": [], "avoid": [] },
  "remarks": ""
}
```

必填最小集：`schedule`（起止）、`user.adults`、`user.departureCity`、`destination.province + city`、`isSelfDriving`。
其余选填——不强迫用户填不必要项。校验：浏览器原生校验 + 后端 422 双重；
返回日期早于出发日期、`mustVisit` 里的空串都会在契约层被处理掉。

### 4.2 返回一：任务与进度

- `POST /api/trips` → `202 { tripId, status:"planning", createdAt }`
- `GET /api/trips/{tripId}/events`（SSE）：`searching / drafting / validating / done / failed`
  前端显示的中文标签：查资料 / 排行程 / 做检查 / 完成 / 失败。
  没有"降级"这类事件——排不出来直接发 `failed`，`message` 就是给用户看的一句话。
  `revising`（标签"调整"）：校验不过、且剩余时间够，就回喂模型重排一轮，这时会发（详见 §5）。
  前端这块做成了**加载态**：罗盘转 + 纸飞机沿虚线飞 + 四步指示（跟着事件点亮）+ 秒表。
- `GET /api/trips/{tripId}` → TripDetail（还在规划时 `days` 为 null，可恢复、刷新不丢）

**done / failed 由接入层在结果存好之后发**，所以前端一收到 done，紧接着 GET 一定拿得到行程。

### 4.3 返回二：TripDetail（行程=时间线方案树）

```json
{
  "tripId": "…", "status": "completed",
  "title": "云南大理 3 日慢游",
  "planMeta": {
    "validated": true,
    "issues": [],
    "notes": ["模型说的酒店「…」不在查到的酒店里，已剔除"],
    "sourceDocs": ["大理攻略.txt"]
  },
  "destination": { "province": "云南", "city": "大理" },
  "budget": { "totalEstimate": 4200, "currency": "CNY", "estimate": true },
  "days": [
    {
      "dayIndex": 1, "date": "2025-08-01", "theme": "洱海环游",
      "segments": [
        {
          "slot": "morning", "slotLabel": "上午",
          "items": [
            {
              "seq": 1,
              "options": [               // ★ 方案集而不是单一路径
                {
                  "poi": { "poiId": "…", "name": "洱海生态廊道",
                           "poiType": "自然", "rating": 4.7,
                           "lat": 25.7, "lng": 100.2 },
                  "durationMin": 180,
                  "transportOptions": [  // ★ 每种方式都预置耗时/价格/理由
                    { "method": "taxi", "durationMin": 20, "price": 25,
                      "recommendReason": "价格与速度平衡", "recommended": true },
                    { "method": "bike", "durationMin": 45, "price": 3,
                      "recommendReason": "骑行比走路快，费用低" }
                  ],
                  "combinationPoi": null
                }
              ],
              "timeRange": { "start": "09:00", "end": "12:00" },
              "unverified": [],          // 模型拿不准、必须提醒用户的事 → 前端灰标
              "sourceRef": { "doc": "大理攻略.txt", "chunkIndex": 2 },
              "locked": false
            }
          ]
        }
      ]
    }
  ],
  "createdAt": "2025-08-01T10:00:00+08:00"
}
```

**交互设计**：节点可展开；换地点=在 `options[]` 里选；换交通=换 `transportOptions[]`，
耗时就地重算——数据全量预置，前端本地切换**零请求**。

**返回质量三标准**：完整性（方案集全量，不"现场再问"）/ 正确性（耗时价格来自确定性计算）/
一致性（时长=活动时长+交通时长，前端只做加减法）。

### 4.4 确认 `POST /api/trips/{tripId}/confirm`

请求是**决策表**，只含用户改过的节点（没动的一律不传；每条至少改一样东西：换地点或换交通）：

```json
{ "decisions": [ { "dayIndex": 1, "slot": "morning", "seq": 1,
                   "chosenPoiId": "…", "chosenTransport": "bike" } ] }
```

返回：`{ "tripId": "…", "spotIntros": [ { "poiId": "…", "name": "…", "intro": "…", "sourceDoc": "…" } ],
"travelTips": ["…"] }`

合并是在**刚生成的那份行程**上做的，所以确认可以重复调用、结果一样（幂等）；
合并后的版本成为之后 GET 拿到的视图。

### 4.5 历史旅游方案（用户确认过的行程，只读）

- `GET /api/plans` → 历史旅游方案列表 `[{planId, title, province, city, startDate, endDate, savedAt}]`（新的在前）
- `GET /api/plans/{planId}` → 那一份**完整的历史行程**（就是存下来的 TripDetail，前端直接渲染；不存在 → 404）

### 4.6 错误体

```json
{ "code": "VALIDATION_FAILED | TRIP_NOT_FOUND | CITY_NOT_FOUND | INTERNAL_ERROR",
  "message": "…", "detail": {} }
```

顶层直接返回，不套 FastAPI 默认的 `{"detail": …}`。
`LLM_TIMEOUT`、`LLM_RATE_LIMIT` 两个码声明了但还没被用上（模型超时现在是走通用失败路径）。

## 5. 后端处理链

```
提交 → ① 契约校验(422) → ② 便宜预检(目录里有 或 语料里有，否则 400)
     → ③ 建任务(planning, 202) → 后台线程跑规划
     → ④ 装配：召回攻略（按城市过滤）+ 候选点（目录有就用目录，没有就从攻略正文抽）
     → ⑤ **并行预取外部事实**（天气 / 酒店 / 车次，线程池，整体预算 25 秒）→ 和候选点、攻略一起进提示词
     → ⑥ 模型排行程（Agent 模式 → 单次生成，每档最多 3 次；**规划这条路关掉思考**）
     → ⑦ 草稿转成品：后端补事实（坐标、交通耗时与价格；打车/自驾走 `tool.py` 的高德数据）、
       剔除目录里没有的地点、**自己修时段撞车 / 开放时间 / 落地时间 / 重复排同一个点**
     → ⑧ 校验（13 类确定性规则）→ 硬问题写进 planMeta.issues（后端自己处理掉的写 notes）
     → ⑨ 结果存内存 → SSE: done
     → ⑩ 前端本地切换 → 用户确认 → 合并决策表 → 返回介绍与建议
```

### 为什么这么快（实测过的三层提速）

| 层 | 做法 | 实测 |
|---|---|---|
| 外部事实 | 天气 / 酒店 / 车次**并行**预取（三个来源互不依赖，串行等于把等待加起来；更要紧的是模型自己调工具每轮就是一次完整生成） | 串行 4.9 秒 → 并行 1.2 秒；少花 1~5 个模型回合 |
| 模型 | 规划这条路 `extra_body={"thinking": {"type": "disabled"}}`：排行程是"照清单和规则填 JSON"，事实由后端补、13 条校验兜底；**解说保留思考** | 一次生成 100 秒 → **15 秒**（输出 22.6k token 里 19.6k 是思考，占 88 秒） |
| 校验 | 能自己修的别麻烦模型（时段撞车、开放时间、落地前不排活动、同一地点重复）→ 少触发回喂那一轮 | 整单 78~217 秒 → **18~42 秒** |

### 模型与后端的分工（本项目最核心的一条设计）

| 谁做 | 做什么 |
|---|---|
| 模型 | 选哪些候选点、一天排几个、先后顺序、每天的主题、每个方案的推荐理由、交通方式（只说 `method`）、拿不准要提醒用户的事 |
| 后端 | 地点的规范名与经纬度（按目录）、交通耗时与价格（按直线距离估算）、时段（按前后顺序推）、剔除目录里没有的地点、7 类校验、预算的 estimate 口径 |

为什么这么分：**模型编不出坐标**，也就不会再出现"坐标中途丢掉、可达性算不出来"那种坑；
耗时不给模型改的机会，"写着 1 分钟、其实十几公里"这类数就没有来源
（原来那条"速度快得不可能"的检查因此被删掉了）。模型的意图保留在两个字段上：
`recommendReason`（为什么选这种交通）和 `recommended`（哪种优先）。

### 校验规则（确定性代码，不靠 LLM）

1. 结构完整：每天三个时段都在
2. 时间连续性：结束晚于开始；不和上一段时间重叠
3. 必去点覆盖：`mustVisit` 里在目录中匹配到的点必须排进行程；匹配不到的在 issues 里说明
4. 地点真实性：行程里的点必须来自本次候选点（模型编的地点在这一步之前已被剔除，这里是二道防线）
5. 可达性：两个节点之间的间隔时间不小于最快交通的耗时（只看默认方案 `options[0]`，
   备选方案的时间差属于"前端切换时要重算时段"的问题，不记成整张行程的硬错误）
6. 营业时间：活动要落在该点的开放窗口内（排不下时 `_fit_open_hours` 会先自己修：往前挪、再压时长）
7. 天数：和请求的日期区间对得上
8. 住宿要盖住整个行程（第一晚到最后一天）
9. 大交通的日期与到达时间要跟行程对得上
10. 模型给的时刻不能跟时段拧着来（"下午 11:00 开始"这类）
11. **时段里得真有内容**：中间的天至少 `MIN_FILLED_SLOTS = 2` 个时段有安排，首末天（可能在赶路）至少 1 个
    —— 这条专治"一天只剩上午有事、其他空着"
12. 同一天同一个地点最多排一次
13. 整趟行程里同一个地点最多排 2 次（防"为了填满时段把几个点来回转"）

另有一条**不算违规的标注**：某个点没有坐标（从攻略正文抽出来的点）时，
写明"可达性这次没校验"以及原因——标注局限，比硬失败或悄悄放过都好。

### 排不出来怎么办（没有"降级兜底"）

- 每档最多试 3 次；总时间预算 150 秒、单次调用 60 秒封顶，剩不到 5 秒就不再开新的一次。
  重试时进度条只说"这次没排好，正在重试"，真实报错（超时、限流、解析不出来）一律写日志。
- 两档都不成 → `GenerationFailed` → SSE `failed` + 一句人能看懂的话。
  **不做"机器凑一张行程顶上"**：那会把"系统坏了"伪装成"排好了"。
- 草稿里一个能用的地点都没有 → 同样算失败。
- 召回失败**不算失败**：按"没有攻略"继续排（目录覆盖这个城市就照样排得出），技术原因记日志。
- 校验不过**不阻断**：先自己修，再回喂一轮，还不行就把问题写进 `planMeta.issues` 让用户看到，行程照给。
  **`issues`（硬问题，影响 `validated`）与 `notes`（后端已经自己处理掉的说明）是分开的**：
  模型编的酒店被剔除、要的交通方式没有改用别的，这些只是说明，不该把整份行程标成"校验未通过"，
  也不该浪费一轮回喂 —— 但两样都要如实显示，不能悄悄咽下去。
  分三层（能自己修的别去麻烦模型）：
  1. **后端自修**（不花模型调用）：模型给了时刻，就用它的时长、把起点往后挪到位 —— 不和上一段撞车、
     不跑到这个时段之外；只往后挪不往前挪（它可能是故意早起看日出）；
     开放时间排不下也在这里修（`_fit_open_hours`：先整体往前挪，挪不动再压游览时间，压到 45 分钟以下才留给校验）；
  2. **回喂重排**：把"上一版草稿 JSON + 问题清单"还给模型，让它只改冲突的地方，重新出一版。
     只回喂**一轮**，且只在问题数真的变少时才采纳；剩余时间不够（< 45 秒）就不试；
  3. 还不过 → 问题写进 `planMeta.issues`，行程照给（红标 + 问题清单）；`planMeta.notes` 单列"已经处理过的"。

### 任务状态机

`planning → completed / failed`。任务表是进程内的一个字典：GET 幂等、SSE 支持多个订阅者、
刷新页面不丢（同一次进程生命周期内）。要多进程部署时必须挪到外部存储 + 队列，现在不需要。

## 6. 外部数据源层（`planning/tool.py`，已写）

五个来源各一个函数，用 LangChain 的 `@tool` 装饰成标准工具（名字、说明、参数 schema 都跟着函数走）。
**谁调它**：两处 —— ① Agent 模式（`build_tools()` 把它们交给 `create_agent`，模型自己决定查什么）；
② 后端自己调（打车耗时是后端算的，住宿的地址与价格也是后端核对时补的）。
给 Agent 的是**包了一层的副本**（`agent._tolerant()`）：工具查不到时把原因当成工具输出还给模型，
不让整轮 Agent 崩掉；后端自己调时用原件，仍然照旧抛错。
（`create_agent` 这一版**不会**替我们兜工具异常 —— 试过 `handle_tool_error=True`，没用，实测工具一抛错整轮就崩。）

- 天气：open-meteo（免费、不用 key），但要坐标 —— 目录里的城市有坐标；目录外的城市得先有地理编码
- 打车 / 自驾的耗时：高德 `v3/direction/driving`，给出路网距离与耗时
- 酒店：RollingGo 的 MCP 服务（`TRAVELE_ROLLINGGO_MCP_URL` + `TRAVELE_ROLLINGGO_API_KEY`，Bearer 认证）。
  它有 3 个工具，只用查列表的 `searchHotels`；它的入参有自己的规矩（只查城市要写成"大理 中国"、
  `placeType` 要与内容一致、住几晚用 `stayNights`），这些在工具内部的"传入数据处理"里补齐；
  返回 `{success, hotelInformationList:[...]}`，`success` 为 false 或列表为空就抛错
- 航班：Aviationstack（`access_key` 写在 `TRAVELE_AVIATIONSTACK_KEY`）。注意它**只给班次与起降时刻，没有票价**；
  入参是机场三字码（HGH、PEK），不是城市名 —— 城市名换码需要另一份数据，这里不猜
- 火车：12306 的 MCP 服务（装 `mcp-server-12306`，本机起 `mcp-12306`，默认 8000 端口，
  地址填 `TRAVELE_RAIL_MCP_URL`）。它提供 7 个工具，我们只用名字带 ticket 的 `query-tickets`；
  它的返回是 `{success, count, trains:[...]}`，"查不到"也走 `success: false` → 工具里翻成报错

两个 MCP 服务都走 **Streamable HTTP**，握手与会话交给官方 `mcp` SDK（`streamable_http_client` +
`ClientSession`），不自己拼 JSON-RPC。**工具名不硬写**：先 `list_tools`，要求名字里关键字全命中、
多个命中取名字最短的那个（RollingGo 的 `getHotelSearchTags` 也含 search+hotel，按"第一个命中"会挑错）。

健壮性（实跑踩出来的）：单个请求 20 秒超时，连不上/超时/429/5xx 退避重试最多 3 次（1→2→4 秒）；
高德还会因为问得太快回 `CUQPS_HAS_EXCEEDED_THE_LIMIT`，这种单独当 `RateLimited` 处理（等一下重试），
另外两次调用之间留 0.4 秒间隔。**"没答上来"才重试，key 不对、没这条路这类重试也没用，直接报。**

一条规矩：**查不到就抛 `SourceError`** —— 不返回 None、不返回空列表、不用估算顶替。
没配（`.env` 值留空）、网络不通、对方说没数据，都算"查不到"。

还在估算、而且确实没有数据源的，只有这三种与价格：

- 步行 4.5 / 骑行 12 / 公交 16（公里/小时），按直线距离估 —— 高德也有步行、骑行接口，要换随时能换；
  公交要城市编码，另说
- 价格一律是估的：打车 13 元起步 + 超过 3 公里每公里 2.6 元；公交 2 元；骑行按里程估；自驾每公里 0.8 元
  —— 高德只给距离与耗时、**不给票价**

接线进度：**打车与自驾已经接进** `planner.transport_options`（距离与耗时用高德的路网数据，
没配 key 就直接报错）；天气、酒店、机票、火车**还没有调用方** —— 住宿与大交通在契约里没有字段，
查回来没地方放，等定了放哪儿再接。

关于 Agent：`planning/agent.py::build_tools()` 仍返回空列表，所以 `make_draft` 每次都**跳过 Agent 模式**
直接走单次生成。这一版有意不做"模型自己调工具"。

## 7. 离线侧（攻略语料管道）与在线衔接

- 已实现，保持原样：切分 1000 / 重叠 100；本地 bge 嵌入；集合 `rag_cosine` **必须余弦度量**；
  metadata 含 `city / source / create_time`；md5 去重；
  城市从正文提取（文件名与正文互相印证 → 开头 200 字窗口 → 全文词频加权）。
- 语料放 `Travele/ingest/corpus/`（现在 22 篇：目录里那 21 个城市**每个都有一篇**，
  另加洛阳），入库后共 42 块。改语料后**要重启后端**，旧进程里是旧快照。
- ⚠️ `ingest/city_extract.py` 的名单是"按城市过滤"的地基：名字必须和 `destinations.json`
  的 city **一字不差**，否则元数据会被打成邻居城市或空标签，检索时静默漏掉。
- 衔接：在线按城市过滤检索 Top-5，相关度低于 0.25 的丢掉（宁可空着，也不塞不相关的）。
- **目的地目录不是准入闸门**：真正的门槛是"有没有语料"。
  目录里没有、但有语料的城市（例如洛阳）改走"从攻略正文抽地点"那条路，
  只是抽出来的点没有坐标 → 可达性跳过并在 issues 里写明。
- 目录（`data/destinations.json`，**21 城 128 点**）提供坐标、开放时间、常规游览时长、一句话介绍；
  其中的 92 个点由 `data/build_catalog.py` 扩充：**名字由人写**（和攻略正文叫法一致，才能对上"引用攻略"），
  坐标 / 评分 / 开放时间来自高德 POI 检索。**目录点太少就排不满日程**（一个城市只有 1 个点时，
  三天行程必然空半天），所以这一层要够厚：现在每城 5~8 个点。
  随机卡片另用 `static/data/spots.json`（21 城 26 张）。两份数据各服务各自的用途，互不影响。

## 8. 长期记忆（已实现：`Travele/memory/memory.py`）

存的是"关于这个人的稳定事实"，不是聊天记录，也不做摘要压缩（内容很少）：

- **偏好**（喜欢 / 忌讳）：走**证据计数** —— 同一条出现 ≥2 次才算长期画像，出现一次不算，
  免得一次偶然的选择被永久记住、之后每次都带偏
- **补充说明**：用户在表单里写的原话，原样存（不摘要、不改写），同一句不重复入库
- **去过的点**：确认过的行程里选中的点（带城市和日期），按 (点, 日期) 去重

存储用标准库 `sqlite3`，一个文件 `Travele/sqlite_data/memory.db`，四张表：
`preferences` / `remarks` / `visited` / **`plans`**（用户确认过的整份行程，JSON 原样存，
"历史旅游方案"那个标签就读它；按 trip_id 覆盖，重复确认不会重复记）。不用中间件、不用 ORM。

**读取**：`memory_text()` 渲染成**固定顺序**的几行中文（喜欢 → 忌讳 → 补充说明 → 去过），
填进 `PlanContext.memory` → 系统提示词的「长期记忆」段。顺序固定是有意的：
同一个人的同一份画像每次渲染必须一模一样，否则提示词的缓存前缀每次都失效。
没有记忆时返回空串，提示词里如实写"（暂无记忆）"。

**写入**：只有一处 —— 用户点"确认行程"之后（`planner.remember_trip`）。
这时才有"最终行程 + 用户的改动"这种干净信号。写失败只记日志、不影响确认
（这是全项目唯一一处"出错了不往上抛"，因为记忆的失败跟用户要看的结果无关）。

现在只有一个本地用户（前端不参与、没有登录），`user_id` 固定成 `"local"`；
以后接账号只要改这一处，表结构不用动。

## 9. 取舍说明（实习叙事）

- **两个 Agent，各有边界**：规划 Agent（带工具多步排行程）+ 解说 Agent（确认后写介绍与建议）。**
  都不上多 Agent 消息风暴**；解说这一层同样是"后端备事实、模型只写文字"，
  出处由后端按攻略正文匹配 —— 模型可以写得好看，但说的事实必须是我们给的。
- **有意不做的四件事**（不是没做完）：① 大交通不跟车站/机场核对（个人项目里做不到"完美"，
  如实标"未核对"比假装准确好）；② 机票票价不实现（没有可靠来源，后端不给模型猜的数、前端注明）；
  ③ 任务不落库（重启丢掉"正在规划的"，确认过的行程在历史里，够用）；
  ④ 长期记忆不做前端面板（它是给 Agent 看的，前端只要能查历史行程）。
- **事实与编排分开**：模型只做它擅长的，正确性交给确定性代码。这是最值得讲的一点。
- **降级不做"假成功"**：宁可直接失败让用户重试，也不给一份机器凑的行程。
- **目录做增强层、不做白名单**：全国几千个县不可能手写，有语料就能排。
- **提示词按 prompt 缓存布局**：规则 + 资料在哪 + 长期记忆 + 输出格式说明（约 5000 字的 JSON schema）
  全放系统消息，需求 + 候选点 + 攻略片段放人类消息——内容相同的前缀越长越容易命中缓存。
  实测换个日期重跑（候选点不变），系统消息那段命中缓存 62%（旧的布局只有 8%）。

## 10. 技术选型

| 层 | 技术 | 在本项目干什么 |
|---|---|---|
| 前端 | 纯 HTML/CSS/JS + `fetch` + `EventSource`；Tailwind CDN + Google Fonts + Lucide | 四个视图、手账质感、方案树、进度、零构建步骤（代价：离线掉样式） |
| 接口层 | FastAPI + Pydantic v2（对外 camelCase、内部 snake_case，别名转换）+ uvicorn | 契约校验(422)、任务创建、SSE、GET、统一错误体 |
| AI 编排 | LangChain：`init_chat_model` / `create_agent` / `PydanticOutputParser` / `ChatPromptTemplate` / `trim_messages` | 模型接入、工具循环、结构化输出、控长度 |
| RAG | langchain-chroma + langchain-huggingface（本地 bge-small-zh-v1.5） | 在线检索直接读离线建好的库 |
| 离线管道 | `ingest/`（Streamlit 上传页 + 切分 + 向量化） | 加攻略走这里 |
| 异步 | asyncio 后台任务 + `asyncio.to_thread` + SSE | 202 立刻回、进度事件、线程里跑阻塞的模型调用 |
| 存储 | 内存（任务与行程）+ Chroma（向量库） | 没有数据库，进程重启即丢 |
| 依赖管理 | uv（`pyproject.toml` + `uv.lock`） | 一键装依赖 |

**已装但没用上的依赖**（写清楚，免得后人以为在用）：`langgraph`（图上编排没用）、`pydantic-settings`。
`httpx` 现在用上了：`planning/tool.py` 的外部请求都走它。

**模型**：`deepseek-v4-flash`，走 OpenAI 兼容接口（`init_chat_model(..., model_provider="openai")`）。
它是**思考型模型**，有两条硬限制/特性：
① **强制 `tool_choice` 会被服务端拒**（实测 400 `Thinking mode does not support this tool_choice`），
所以 LangChain 的 `function_calling` 结构化输出、`create_agent` 的 `response_format` 两条路都不通；
能走通的是"工具照给（模型会自己决定调用）+ `response_format=json_object`"。
② **思考可以关**：`extra_body={"thinking": {"type": "disabled"}}` —— 规划这条路就是关着跑的（见 §5 提速那节），
解说不关。

## 13. 主要风险与对策

- **LLM 幻觉（地点/价格/时间）** → 模型不填事实；目录外的地点直接剔除；7 类校验；问题清单明示给用户
- **思考型模型的工具限制** → 工具照给但不强制；结构化输出走 `json_object` + Parser
- **模型排不出来** → 直接失败并让用户重试，不伪装成功；技术原因只进日志
- **缺数据** → 提交时就拦（城市既不在目录又无语料 → 400），并在错误信息里告诉用户该补什么
- **交通耗时与价格** → 打车与自驾在配了高德 key 后是**路网**数据；其余（步行/骑行/公交）与所有价格
  仍是估算（高德不给票价），预算上带 `estimate` 标记，不假装是真实数据
- **token 成本** → 随机发现零 LLM、提示词按缓存布局、候选点与攻略在人类消息里只出现一次
- **简历叙事风险（"套壳 ChatGPT"）** → 确定性部分（校验器、事实补齐、方案树、失败处理、前端交互）
  占主要工程量，且每一处都有可讲的取舍理由
